# 项目阶段流程

本流程服务于“恶搞讽刺 Demo 的公开源码仓库与可玩网页”交付。完整体验目标约 1—2 小时，实际时长需要试玩验证；阶段流程保持轻量。任务状态统一记录在 [TODO.md](../TODO.md)。

## 版本与阶段

Demo 设计先覆盖从初创到结局的主要情境，再按可玩结果实现。首个原型验证核心循环与笑点，公开 Demo 实现承诺范围；不以完整商业游戏的系统规模作为阶段门槛。

| 阶段 | 主要产物 | 进入下一阶段的条件 |
| --- | --- | --- |
| 设计 | 剧本、经营规则、多结局、视觉、声音、技术与原型范围 | 当前里程碑的玩家流程、资源变化、例子与验收明确，未决项已列出 |
| 评审 | 用户产品反馈、表达方案反馈、内部规则与技术核查记录 | 背景、剧本和玩法已获用户确认，画面音乐表达已评审，影响实施的问题已解决，采用方案写回设计 |
| 开发 | 可运行的完整功能切片及必要验证 | 当前切片能实际操作，规则与设计一致，具备交给测试的运行方式 |
| 测试 | 规则验证、完整流程验证、真实试玩和修复记录 | 当前版本的阻塞缺陷修复，声明范围有证据，未覆盖范围明确 |
| 上传发布 | GitHub 源码、README、许可证、网页和发布记录 | 源码已推送，部署成功，线上关键流程验证通过 |
| 持续优化 | 真实反馈、优先级、下一版本范围 | 选出有明确验收条件的改动，重新进入设计或相关阶段 |

每个里程碑执行适用阶段。原型即使对外发布，也只标记为原型版本；[PROJECT.md](../PROJECT.md) 的最终交付标准仍然有效。阶段发现问题时回到负责该问题的阶段，修复后重新核对受影响的验收。

## 里程碑顺序

1. 设计基线：先供用户评审背景、完整故事、玩法和结局，再评审画面音乐表达，完成受影响的规则与技术核查。
2. 首个可玩原型：研发、发布、榜单、收入、扩张成立，并有真实试玩反馈。
3. 可分享 Demo：实现精选经营流程、多结局、必要画面与声音。
4. 首次 Demo 公开发布：仓库、网页、许可、说明与线上验证齐全。
5. 后续版本：以实际反馈决定内容。

不提前承诺开发日历。工作量估计在范围和素材生产方式明确后记录。

## 评审记录

每份记录说明日期、对象版本、参与者、评审方式、验收、发现的问题、处理结果和未验证范围。有 Git 提交时记录提交标识；没有提交时明确记录文件范围和本地工作区状态。

用户产品评审与内部核查分别记录。用户先判断背景、故事、操作和成长是否符合目标，再判断画面音乐表达；内部核查验证规则、实现方案和证据。内部检查可以并行准备，但其通过不能替代用户产品确认。已确认的方向和角色不重复请求确认。

设计自检与独立评审分别标注。没有独立参与者时不能声称做过独立评审。只有实际执行的验证才能写“通过”。

当前阶段满足验收后，在 TODO 更新状态并继续已授权工作。产品方向、费用、公开身份和许可选择有实质未决项时，提出具体问题；常规实现与修复不重复请求确认。

## 六项设计工作的交付要求

- 剧本：章节、角色、事件、触发条件、玩家操作、经营后果、结局和跳过方式。
- 机制：研发、员工、算力、榜单、收入、支出、用户反馈的规则、结算顺序和数值例子。
- 美术：场景构图、界面信息层级、配色、像素尺寸、字体、动画和可编辑原文件。
- 声音：原创主题、场景曲目、循环、事件音效、音量、静音以及可编辑谱面或合成参数。
- 素材与名称：来源、许可、署名、虚构角色与品牌识别性检查，见 [ASSET_RIGHTS.md](ASSET_RIGHTS.md)。
- 创意：原始输入、来源、讽刺对象、可操作后果、实现成本、采用状态和设计落点，见 [IDEAS.md](IDEAS.md)。

## 开发与测试

按玩家可观察的结果拆分，例如“首次发布改变排名并带来资金”，让每个切片包含必要界面、规则和验证。避免先建设没有当前消费者的通用游戏框架。

规则验证重点包括：
- 不足资金的操作不会扣出无意产生的负数。
- 算力占用不超过容量；模型完成后释放相应占用。
- 排名并列、对手发布、规则更新具有确定结果。
- 融资不会因重复点击或重新读档重复到账。
- 暂停和读档不会额外结算工资、训练和订阅。
- 相同起始条件与相同操作可以重现问题。
- 多结局条件覆盖完整且优先级一致；客户评价不意外成为主要胜负条件。

真实试玩单独记录理解程度、第一次发布时间、卡住的位置、是否愿意再次发布。自动测试不能证明游戏有趣；作者自玩不能冒充外部试玩。

## 发布

拟采用静态网页托管。GitHub Pages 可通过 GitHub Actions 构建并发布；这是候选方案，实施时确认仓库设置与最新官方用法。[GitHub 官方发布说明](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)

发布前核对实际资产与许可、构建结果、仓库归属和版本说明。逐项检查待上传文件中的私人路径、内部链接与原始交接内容，确定适合公开的范围；本地留存不等于可以直接上传。发布记录包含源码提交、版本、部署结果、实际 URL、在线检查和已知限制。重新部署保留可定位的源码版本；涉及存档格式变动时说明兼容策略。

## 上下文与归档

每次任务结束更新当前文档、TODO 和 CONTEXT。重要取舍追加到 DECISIONS，评审与验证记录保存到 docs/reviews。后续发布记录也保存在该目录，按日期与任务命名。

Git 保存文件历史，远端推送保存可核验的远端副本。每次接续任务核对分支、修改、提交和远端，明确哪些内容只在本地。

README 面向玩家与开发者；CONTEXT 面向接续任务；二者均链接权威设计，不复制整份规则。
